updated: 2026-11-11T12:52

- (requirement) R1 (experience Foundation › Settings axes; design Brand & Style): style, theme, density and the accessibility settings are independent; changing one leaves the others as set, and density persists across style switches.
- (requirement) R2 (experience Style Contract › Free mix; design Brand & Style): any built-in or third-party theme renders in any built-in style at any density with nothing tuned per pairing.
- (requirement) R3 (experience Style Contract; design Brand & Style › The style contract): a style places or explicitly hides each fixed region (titlebar, nav, list, reading, rail, overlay, toast) with the shared feature components, and sets only radius, spacing, row heights per density and component variants, reading role tokens only.
- (requirement) R4 (design Colors › Role tokens, Categorical palette; Typography; Elevation & Depth): every theme defines every contract role (colour incl. the 8-colour categorical palette, typography with line height, the three shadow roles) in each variant it ships.
- (requirement) R5 (design Colors › Theme catalogue, Variants): nine bundled built-in themes (Classic, Aubergine, Taiga, Darkside, Less-is-more, Loft, Volt, Ember, Dusk) each ship light and dark at standard and high contrast, never fail to load and never show derived.
- (requirement) R6 (design Components › Style catalogue; Layout & Spacing › Window chrome and minimum width, Density): five built-in styles (Classic, Loft, Taiga, Darkside, Less-is-more) each ship with their own minimum width, row height per density, title bar and layout-mode rule (Loft always split pane).
- (requirement) R7 (experience Style Contract › Built-in coverage; Information Architecture › Surfaces every style must lay out): every surface this initiative ships is laid out by all five built-in styles before it is released.
- (requirement) R8 (design Components › Loft mail surfaces; Layout & Spacing › Loft style layout; experience Component Patterns › Loft mail surfaces): the Loft style and Loft theme deliver the Loft mail view (top bar with app mark, search pill and overlay, bell placement, gear, account chip; sidebar; message list with the overhanging selected card; reading card with right rail; compose card) with the behaviour EXPERIENCE gives each.
- (requirement) R9 (experience Information Architecture › Where each setting lives; Component Patterns › Appearance page, Shared components): Preferences › Appearance sets style, theme, mode, Increase contrast, density, text size, font and Adapt email colours with a preview of real components on fixture data in the pending look; the Preferences sheet keeps one shared layout in every style; the theme-picker modal is gone.
- (requirement) R10 (experience Interaction Primitives › Two apply models; State Patterns › Appearance): style, theme, density and font change only the preview until Apply; Revert or Esc discards (Undo for 5s) and leaving discards silently; Mode, Increase contrast, text size and Adapt email colours apply at once.
- (requirement) R11 (experience State Patterns › Appearance; Accessibility Floor › Focus, Screen readers): Apply cross-fades after the new look paints, keeps focus where it was, and announces the whole new look.
- (requirement) R12 (experience Information Architecture › Onboarding looks step; Key Flows › Flow 1, Flow 3): first launch after account setup offers the Loft, Classic and Darkside looks plus text size and Increase contrast, once per install; Continue applies the pick, Skip lands on Loft.
- (requirement) R13 (experience Information Architecture › Where each setting lives; Responsive & Platform › OS appearance): Mode Auto follows the OS light/dark setting live on macOS, Windows and Linux; Light and Dark pin it.
- (requirement) R14 (experience Accessibility Floor › Increase contrast; design Colors › Contrast pairs): Increase contrast (Follow system, On, Off; tracking prefers-contrast live) swaps every theme to its high-contrast variant, and every high-contrast variant passes every pair in Contrast pairs.
- (requirement) R15 (design Colors › Forced colours and Increase contrast borders; experience Accessibility Floor › Forced colours): forced colours are honoured, and Increase contrast adds border-strong edges wherever separation is by shadow or tint only.
- (requirement) R16 (experience Accessibility Floor › Text size; design Typography): text size (87.5-150% in 12.5% steps) scales all type and reflows layout, stacks under window zoom, and starts from the OS text scale where Electron exposes it (100% on macOS).
- (requirement) R17 (design Typography; experience State Patterns › OS signals): font override replaces the theme typeface app-wide; a missing font falls back to the theme default with a toast.
- (requirement) R18 (design Layout & Spacing › Density; experience Accessibility Floor › Pointer targets): density (Compact, Comfortable, Spacious) scales each style's spacing roles and applies that style's row height for the level; every message row keeps a 24px pointer target.
- (requirement) R19 (experience Style Contract › Obligations every style meets; Accessibility Floor): every style meets the shared obligations: two-tone focus ring at 3:1 never clipped, RTL via logical properties, instant motion under reduced motion, never colour alone, dir=auto on mixed scripts, and the listed screen-reader semantics.
- (requirement) R20 (experience Responsive & Platform › Window chrome; design Layout & Spacing › Window chrome and minimum width): the window is frameless on macOS, Windows and Linux; each style draws its title bar with OS controls placed per OS, and the top bar is the drag region.
- (requirement) R21 (experience Responsive & Platform › Reflow ladder): below a style's minimum width its regions collapse along the reflow ladder, holding at 150% text plus zoom.
- (requirement) R22 (experience Email Body Rendering; Component Patterns › View original toggle): in dark mode email bodies are adapted so text meets the active contrast floor with images untouched; View original is per message, remembered per sender per account; replies, forwards and print use original colours; an app-wide switch turns adaptation off.
- (requirement) R23 (experience Theme Authoring › Format, Validation, Identity): a third-party theme is one DTCG .tokens.json file identified by $metadata.id; a file breaking the validation rules or reusing a built-in id or name is rejected with an error naming file and line, and is never copied.
- (requirement) R24 (experience Theme Authoring › Location, Live reload, Last valid cache): saving a file in the themes folder reloads that theme in the app and the preview after 300ms; a theme that fails to load falls back to its last valid version, then Loft, with an error toast.
- (requirement) R25 (experience Theme Authoring › Install, export, remove; Component Patterns › Install theme…): users install a theme from a file (it becomes the pending theme; clashes ask Replace or Keep both), export a copy of a built-in, and remove a third-party theme.
- (requirement) R26 (experience Theme Authoring › Partial themes; State Patterns › Theme files): a third-party theme's missing variants are derived in OKLCH, missing roles filled from Classic and failing high-contrast pairs re-derived, and its swatch shows derived.
- (requirement) R27 (experience Style Contract › Community styles; Theme Authoring › Styles): a public style API lets plugin packages add styles; a feature a community style doesn't cover renders in Classic's arrangement and its card names what it doesn't cover.
- (requirement) R28 (experience State Patterns › Upgrade): upgrading maps each legacy built-in theme to its style and theme, lands community LESS-theme users on Classic with a toast naming the theme, shows the New: Appearance toast, leaves core.themes untouched, keeps styles.less loading, and keeps plugins built on ui-variables working through a shim.
- (requirement) R29 (experience Theme Authoring › Docs): a user-facing theme author guide exists and Appearance links to it.
- (requirement) R30 (design Colors › Categorical palette): folder, calendar and avatar colours come from the categorical palette by a hash of id or email, and a user override is stored as a palette index so it resolves in every theme and variant.
- (requirement) R31 (experience Component Patterns › Toast): toasts stack at most three, de-duplicated by key; info toasts auto-dismiss after 5s as status; error toasts persist as alerts and carry the word Error.
- (requirement) R32 (experience Verification Matrix; design Layout & Spacing › Loft style layout › Reference scale): all 540 combinations get screenshots and overflow checks, contrast pairs are checked directly, axe runs on high-contrast variants, each style passes a by-eye check in the real Electron app at its native theme and density, and Loft passes the scale-normalised diff against imports/loft-01.webp.
- (constraint) Public open-source release people install: first-run defaults matter, the theme and style APIs face users, accessibility is not optional (experience Foundation › Stakes).
- (constraint) Ownership: the theme owns colour, typography incl. line height and shadow; the style owns layout, regions, radius, spacing, row heights, title bar and minimum width; a style never names a theme or a hex, a theme never changes layout, corners or spacing (design Brand & Style; Do's and Don'ts).
- (constraint) Styles cannot replace components: each feature is written once and registers into regions, not styles (experience Style Contract › Shared components, Regions).
- (constraint) Five-style coverage is a release blocker (experience Style Contract › Built-in coverage).
- (constraint) Standard contrast stays reference-exact (Loft mockup-exact) even where AA fails, an accepted risk kept safe by onboarding offering Increase contrast and the Increase contrast label passing AA in every theme; never quietly fix standard ratios (design Colors › Contrast pairs; experience Foundation › Accepted risks).
- (constraint) Theme files are W3C DTCG JSON, one file per theme with four variant groups light, dark, light-hc, dark-hc, holding only colour, dimension, font-family, shadow and font-weight values (experience Theme Authoring › Format, Validation).
- (constraint) Third-party themes come only through token files; community LESS themes stop loading (experience Foundation › Third party).
- (constraint) New settings use new keys; the legacy core.themes key is left untouched so a downgrade still works (experience State Patterns › Upgrade).
- (constraint) The open-source build bundles only redistributable faces (Jost, Ubuntu, Inter, Source Serif); Nylas-Pro renders only when the private nylas-private-fonts package is present (design Typography; Colors › Theme catalogue).
- (constraint) All style layout uses logical properties and every style supports RTL (design Layout & Spacing › Loft style layout; Do's and Don'ts).
- (constraint) Each style owns a frameless title bar on all three OSes, an accepted risk reaffirmed (experience Foundation › Accepted risks).
- (constraint) Loft is the only name for that style and theme; Loft's top bar shows the app's own mark (design Brand & Style).
- (constraint) The spines win over mockups and imports; DESIGN owns tokens and visuals, EXPERIENCE owns behaviour (design structure note; experience preamble).
- (constraint) Loft's CSS token values are canonical; imports/loft-01.webp is checked for composition, proportion and colour at its own scale, not as a pixel target (design Layout & Spacing › Loft style layout › Reference scale).
- (constraint) Images in email bodies are never altered in dark mode (design Do's and Don'ts; experience Email Body Rendering).
- (constraint) Microcopy follows the tone rules and strings table (experience Voice and Tone).
- (assumption) Calendar and Contacts features, and the notifications feature behind Loft's bell, are outside this initiative; it ships the regions they register into and Loft's visual spec for them, because EXPERIENCE says Calendar and Contacts may be scheduled under the state-of-the-art initiative and the bell opens its own epic.
